# Метрики и их объективность

Все метрики считаются за полуинтервал `[from, to)` и сравниваются с **предыдущим периодом той же длины**.
Код расчёта — `internal/metrics`, описания для интерфейса — `internal/metrics/definitions.go`.
Метрика без данных (например, нет MR) показывается как «—», а не как 0: отсутствие данных не выдаётся за результат.

## Подготовка данных

| Правило | Зачем |
|---|---|
| Merge-коммиты не считаются коммитами и не дают строк | их diff повторяет уже учтённые изменения |
| Исключаются `vendor/`, `node_modules/`, `dist/`, `build/`, lock-файлы (`go.sum`, `package-lock.json`…), минифицированный и сгенерированный код (`*.pb.go`, `*.min.js`…), бинарные файлы | это не работа разработчика; настраивается `EXCLUDE_PATTERNS` |
| Исключаются боты (`[bot]`, dependabot, renovate, github-actions…) | автоматические обновления зависимостей не являются работой команды |
| Идентичности сливаются: email из Git, логин и имя из Т1 Код → один автор; ручное объединение в настройках | один человек не должен «делиться» на нескольких |
| Даты до 2000 года или в будущем → берётся дата коммиттера, иначе коммит пропускается | защита от сломанных часов |
| Время коммита — в часовом поясе автора | корректные «рабочие часы» для распределённых команд |

## Поток

| Метрика | Формула | Лучше |
|---|---|---|
| Коммиты | число коммитов за период (без merge) | контекст |
| Активные человеко-дни | Σ по разработчикам числа дней с ≥1 коммитом | контекст |
| Коммитов на активный день | коммиты / человеко-дни | контекст |
| Смёрдженные MR | MR с `merged_at` в периоде | ↑ |
| Lead time MR | медиана и p85 от `created_at` до `merged_at`, часы | ↓ |
| Время до первого ревью | медиана от создания MR до первого комментария/approve другого участника | ↓ |
| Закрытые задачи | задачи с `closed_at` в периоде | ↑ |
| Cycle time задачи | медиана от создания до закрытия | ↓ |

## Качество

| Метрика | Формула | Лучше |
|---|---|---|
| Размер коммита | медиана (добавлено + удалено) строк | ↓ |
| Доля больших коммитов | коммиты > 500 строк / все | ↓ |
| Размер MR | медиана строк diff влитых MR | ↓ |
| Доля больших MR | MR > 400 строк / влитые MR с известным размером | ↓ |
| Rework rate | строки в файлах, которые **тот же автор** менял ≤ 21 дня назад / все строки | ↓ |
| Коммиты с тестами | коммиты, затронувшие тестовые файлы / коммиты с кодом | ↑ |
| Качество сообщений | Conventional Commits или тема 10–100 символов, не «fix/wip/update» / все | ↑ |
| Связь с задачами | коммиты со ссылкой `#12`, `PROJ-34`, `!5` / все | ↑ |
| Покрытие ревью | влитые MR с ≥1 ревью / влитые MR | ↑ |

## Команда

| Метрика | Формула | Лучше |
|---|---|---|
| Bus factor | владелец файла — автор наибольшего числа изменённых строк; «живые» файлы — менявшиеся за последний год; bus factor = минимум людей, владеющих > 50% живых файлов | ↑ |
| Проведено ревью | MR, в ревью которых участвовал разработчик | ↑ |
| Работа вне рабочего времени | коммиты в будни вне `WORKDAY_START..WORKDAY_END` / все | ↓ |
| Работа в выходные | коммиты в сб–вс / все | ↓ |

Дополнительно на дашборде: тепловая карта «день недели × час», горячие точки (файлы с наибольшим числом
изменений и авторов), таблица владения кодом.

## Почему это объективно

1. **Строки кода — не мера продуктивности.** Они показываются только как контекст; в баллах Zerocracy строки
   вообще не участвуют, а большой размер MR даже штрафуется.
2. **Медианы вместо средних.** Один «зависший» MR или гигантский коммит не искажает картину; p85 показывает хвост.
3. **Нормирование.** Интенсивность считается на активный день, а не на календарный.
4. **Сравнение с собой.** Тренды строятся к прошлому периоду той же длины, а не рейтингом людей между собой.
5. **Шум исключён.** Merge-коммиты, зависимости, сгенерированный код, боты.
6. **Прозрачность.** Формула каждой метрики доступна в интерфейсе (подсказка и таблица «Все метрики и как они
   считаются») и через API `/api/metrics/definitions`; результаты воспроизводимы на тех же данных.
7. **Разные измерения.** Скорость (lead time), качество (размер, тесты, ревью) и устойчивость (bus factor,
   переработки) рассматриваются вместе — «разогнать» одну метрику в ущерб другим заметно.

## Пороги рекомендаций

| Условие | Важность |
|---|---|
| Bus factor = 1 при ≥ 10 активных файлах | критично |
| Lead time MR > 72 ч; первое ревью > 24 ч; > 30% больших MR; покрытие ревью < 70% | внимание |
| Коммиты с тестами < 20%; rework > 25%; работа вне времени + выходные > 25% | внимание |
| Качество сообщений < 60%; связь с задачами < 30%; > 20% больших коммитов; hotspot ≥ 10 изменений от ≥ 3 авторов | инфо |
| Ухудшение/улучшение ключевой метрики > 30% к прошлому периоду | внимание / хорошо |

Правила — `internal/analysis/analysis.go`.
