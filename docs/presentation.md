# Презентация и сценарии показов TeamPulse

Структура выступления для пяти Показов и финальной защиты. Связанные документы: [MVP](mvp-and-user-stories.md) · [wireframe](wireframe.md) · [backlog](backlog.md) · [метрики](metrics.md) · [Zerocracy](zerocracy.md) · [безопасность](security.md).

Общие правила: 10–12 минут на показ, 2–3 минуты на вопросы; говорят по очереди все четверо (TL — постановка и итоги, BE — данные и метрики, FE — интерфейс, QA — качество). Демо всегда на подготовленных данных, запасной вариант — записанное видео/скриншоты.

## Показ 1 — Планирование и дизайн (спринт 1)

**Слайды**
1. Проблема: оценка команд субъективна или сводится к «строкам и коммитам».
2. Команда и роли (TL/BE/FE/QA), ритуалы, доска в Сфера.Задачи.
3. Пользователи и две обязательные истории (руководитель, разработчик).
4. MVP: что входит и что нет ([mvp-and-user-stories.md](mvp-and-user-stories.md)).
5. Стек: Go, SQLite, html/template + Chart.js, go-git; почему один статический бинарник.
6. Дизайн данных: формат метрики (ключ, единица, направление «лучше», формула), структура отчёта.
7. Wireframe: дашборд и блок «Мой вклад» ([wireframe.md](wireframe.md)).
8. Правила безопасности: роли, токены, SSRF, CSRF.
9. Бэклог спринта 2.

**Демо:** показать доску с эпиками и wireframe; демонстрации кода нет.

## Показ 2 — Парсер и базовый дашборд (спринт 2)

**Слайды:** архитектура (парсер -> SQLite -> метрики -> UI); как парсится история (инкрементально, без merge-коммитов, без vendor/lock); первые метрики; тесты; план спринта 3.

**Демо-скрипт**
1. `make run` (dev-режим, `ALLOW_LOCAL_REPOS=true`), открыть `http://localhost:8080`.
2. Добавить проект: имя `go-billy`, URL `https://github.com/go-git/go-billy`, ветка по умолчанию.
3. Нажать «Синхронизировать» -> статус «синхронизация…», затем «ok».
4. Открыть дашборд: KPI, график коммитов, таблица «Все метрики и как они считаются».
5. Повторная синхронизация: показать, что обрабатываются только новые коммиты.
6. `make test` — зелёные тесты.

## Показ 3 — Т1 Код, отчёты, интерактив (спринт 3)

**Слайды:** интеграция с Т1 Код (GitLab API v4: MR, ревью, задачи, пагинация, retry на 429/5xx); метрики потока (lead time, время до ревью); отчёты HTML/MD/CSV/JSON; интерактивный дашборд; «Мой вклад»; тестирование с реальным репозиторием; **как обеспечивается объективность метрик** (раздел ниже).

**Демо-скрипт**
1. Дашборд `go-billy` за 90 дней: переключить пресеты, задать произвольные даты, выбрать команду.
2. Навести курсор на KPI-плитку — показать формулу; открыть таблицу «Все метрики».
3. Открыть тепловую карту и блок «Владение кодом».
4. Кликнуть имя разработчика -> «Мой вклад».
5. «Отчёты» -> создать отчёт -> открыть HTML -> скачать `?format=csv`, `?format=md`, `?format=json`.
6. Подключённый проект Т1 Код (или mock): MR, ревью, lead time.
7. Терминал: `make test-integration` — сценарий на реальном репозитории.

## Показ 4 — Тренды, рекомендации, защита, деплой (спринт 4)

**Слайды:** тренды против собственного прошлого периода; правила рекомендаций и уровни; защита от плохих данных (будущие даты, пустой репозиторий, неверная ветка, лимит коммитов, частичная синхронизация); Zerocracy (политика, журнал, подбор исполнителей); безопасность; Docker и публичный деплой; документация.

**Демо-скрипт**
1. Дашборд: блок «Выводы и рекомендации», дельты и вердикты (▲▼).
2. Добавить проект с неверной веткой -> понятная ошибка; пустой репозиторий -> предупреждение; URL `http://127.0.0.1` -> отказ.
3. Блок Zerocracy: баллы, «из чего сложились», журнал начислений; показать `policy.example.json`.
4. Блок «Распределение открытых задач» — кандидаты и причины.
5. Войти как viewer: нет кнопок админа; попытка POST -> 403.
6. Публичный URL, `GET /healthz`; `docker compose up -d`.

## Показ 5 — Финал и защита (спринт 5)

**Слайды**
1. Проблема и решение в одной картинке.
2. Что сделано по спринтам (5 результатов).
3. Демо-сценарий (ниже).
4. Объективность метрик.
5. Архитектура и безопасность.
6. Качество: покрытие тестами, регрессия, интеграционный сценарий.
7. Ограничения и развитие (Jira/GitHub, уведомления, SSO, PostgreSQL).
8. Выводы и вклад каждого участника.

**Финальное демо (7 минут)**
1. Публичный стенд: список проектов, карточка `go-billy`, актуальный статус синхронизации.
2. Дашборд за 30 дней: KPI, тренды, рекомендации, графики.
3. Сравнение периодов: сменить период, показать дельты.
4. «Мой вклад» и баллы Zerocracy с журналом.
5. Создать отчёт, скачать CSV.
6. Настройки: команда, объединение авторов, эффект на метриках.
7. Тёмная тема и мобильная ширина.

## Как обеспечивается объективность метрик

| Принцип | Как реализовано |
|---|---|
| Только значимый код | Merge-коммиты не считаются; vendor, lock-файлы и сгенерированный код исключены из размеров (`EXCLUDE_PATTERNS` расширяет список) |
| Без «шума» ботов | Коммиты и MR ботов (dependabot, renovate, `[bot]`) исключены из метрик |
| Устойчивая статистика | Для времён и размеров берутся медианы и p85, а не средние — единичные выбросы не искажают картину |
| Нормализация | Ритм считается на активный человеко-день, а не на календарь: отпуск и неполная занятость не «штрафуются» |
| Сравнение с собой | Тренд — против предыдущего периода той же длины для той же команды/автора, а не «рейтинг людей» |
| LOC только как контекст | Строки кода не используются как мера продуктивности; коммиты и объём помечены «Neutral» |
| Прозрачные формулы | Описание каждой из 22 метрик — в интерфейсе и в [metrics.md](metrics.md); правила рекомендаций читаемы |
| Единая идентичность | Объединение дублей авторов и связка Git-автор <-> пользователь провайдера |
| Воспроизводимость | Журнал начислений Zerocracy детерминирован: те же данные и политика дают те же баллы |
| Защита от плохих данных | Отбрасываются даты из будущего и аномальные, лимит коммитов, предупреждения вместо тихих ошибок |
| Учёт условий | Рабочие часы настраиваются (`WORKDAY_START/END`), время считается по часовому поясу автора |

## Вероятные вопросы жюри

| Вопрос | Ответ |
|---|---|
| Можно ли накрутить метрики? | Мелкие бессмысленные коммиты не увеличивают баллы: баллы даёт результат (влитые MR, ревью, закрытые задачи), число коммитов — нейтральная метрика; штрафуются MR без ревью и огромные MR. Качество сообщений и связь с задачами сверяются автоматически |
| Почему не «строки кода»? | LOC зависит от языка, стиля и генерации. Используем её только как размер изменения для качества (маленькие MR лучше ревьюятся) |
| Не превращается ли это в слежку за людьми? | Сравнение идёт с собственным прошлым, а не между людьми; формулы открыты; viewer видит те же данные; баллы не привязаны к выплатам |
| Как обрабатываются разные e-mail одного человека? | Ручное объединение авторов в настройках и автосвязка Git <-> провайдер |
| Что если провайдер недоступен? | Git-часть считается, синхронизация помечается предупреждением; запросы повторяются при 429/5xx |
| Как защищены данные и токены? | Токены провайдера шифруются ключом `APP_SECRET`; роли, CSRF, защита от SSRF/open redirect, заголовки безопасности — см. [security.md](security.md) |
| Почему SQLite и Go? | Один статический бинарник без внешних зависимостей, distroless-образ, простой деплой; для масштаба — вынести хранилище в PostgreSQL |
| Как проверялось на реальных данных? | Интеграционный тест на публичном репозитории (`make test-integration`) и ручные прогоны по чек-листу регрессии |
| Что такое Zerocracy в проекте? | Прозрачная политика баллов «за результат» (JSON) и автоподбор исполнителей по опыту и загрузке; см. [zerocracy.md](zerocracy.md) |
| Как это масштабировать? | Инкрементальный разбор, фоновые синхронизации, лимиты; дальше — PostgreSQL, очередь задач, кэш агрегатов |
| Как подключить другую систему задач? | Через интерфейс провайдера (`internal/provider`): реализовать выборку MR, ревью и задач |
| Что не реализовано? | SSO/LDAP, уведомления, ML-прогнозы, другие VCS-провайдеры — в плане развития |
