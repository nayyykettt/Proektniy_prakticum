# MVP и пользовательские истории TeamPulse

Связанные документы: [метрики](metrics.md) · [архитектура](architecture.md) · [безопасность](security.md) · [Zerocracy](zerocracy.md) · [wireframe](wireframe.md) · [backlog](backlog.md).

## 1. Цель и проблема

**Проблема.** Оценка эффективности команд разработки чаще всего субъективна («кажется, команда буксует») или опирается на «дежурные» показатели — число коммитов и строк кода, которые легко накрутить и которые не отражают ценность работы. Руководитель не видит узких мест процесса, разработчик — своего вклада в общий результат.

**Цель продукта.** TeamPulse — сервис, который автоматически собирает данные из Git-репозитория и системы «Т1 Код» (GitLab API v4-совместимой), считает прозрачные метрики потока работы, качества и командной устойчивости, сравнивает команду **с ней самой в прошлом периоде**, формирует рекомендации и отчёты и начисляет баллы по принципам Zerocracy (за результат, а не за время).

**Ценность.**
- руководитель получает объективную картину и конкретные рекомендации, а не «рейтинг людей»;
- разработчик видит свой вклад и то, как считаются баллы;
- расчёты воспроизводимы: любая цифра раскрывается до формулы и журнала событий.

## 2. Персоны

| Персона | Роль в системе | Задачи | Что важно |
|---|---|---|---|
| **Руководитель** (Team Lead / PM) | `admin` — полный доступ | Подключает проекты, запускает синхронизацию, смотрит метрики и тренды, скачивает отчёты, настраивает команды и объединение авторов | Объективность, сравнимость периодов, отсутствие «накрутки» |
| **Разработчик** | `viewer` — только просмотр | Открывает страницу «Мой вклад», проверяет свои баллы и журнал начислений | Прозрачность формул, справедливость, отсутствие слежки за людьми |
| **Интегратор / CI** (вспомогательная) | Bearer API-токен | Забирает метрики и отчёты через REST JSON | Стабильный API |

## 3. Границы MVP

| Входит в MVP | Не входит (вне MVP) |
|---|---|
| Подключение репозитория по HTTPS-URL, клонирование и инкрементальная синхронизация | Поддержка SVN/Mercurial |
| 22 метрики (поток, качество, команда), сравнение с прошлым периодом | ML-прогнозирование, персональные «рейтинги людей» |
| Интеграция с «Т1 Код»: MR, ревью, размер MR, задачи, назначение задачи | Интеграции с Jira, GitHub Issues, Slack/e-mail-рассылки |
| Дашборд, страница «Мой вклад», отчёты HTML/MD/CSV/JSON | Мобильное приложение, экспорт в PDF |
| Рекомендации на основе правил | Автоматическое изменение чужих данных без подтверждения |
| Zerocracy: политика баллов, журнал, подбор исполнителя | Денежные выплаты и KPI-премирование на основе баллов |
| Роли admin/viewer, API-токен, CSRF, защита от SSRF | SSO/LDAP, многопользовательские учётные записи |
| Автосинхронизация и автоотчёты по расписанию | Горизонтальное масштабирование (SQLite, один экземпляр) |
| Docker, docker-compose | Kubernetes-манифесты |

## 4. Пользовательские истории

Формат критериев приёмки: Given / When / Then. Тесты — см. [test-cases.md](test-cases.md).

### US-01. Объективные метрики команды (обязательная)
**Как руководитель, я вижу объективные метрики производительности команд.**

- Given проект подключён и синхронизирован, When я открываю дашборд проекта, Then вижу KPI-плитки, графики и таблицу «Все метрики и как они считаются» с формулой каждой метрики.
- Given выбран период, Then каждое значение сравнивается с предыдущим периодом той же длины с указанием дельты и вердикта (лучше / хуже / без изменений).
- Given в истории есть merge-коммиты, боты, vendor- и lock-файлы, Then они не влияют на значения метрик.
- Given данных за период нет, Then показывается понятное пустое состояние, а не нули/ошибки.

### US-02. Мой вклад (обязательная)
**Как разработчик, я вижу свой вклад в общий результат.**

- Given я вошёл под ролью viewer, When нажимаю своё имя в таблице «Вклад разработчиков», Then открывается страница «Мой вклад» с моими метриками, тепловой картой активности и баллами Zerocracy.
- Then виден состав баллов («из чего сложились») и журнал начислений со ссылками на MR/задачи.
- Then доступна ссылка «← Весь проект» с сохранением выбранного периода.

### US-03. Синхронизация данных
**Как руководитель, я запускаю синхронизацию проекта и вижу её статус.**

- Given я admin, When нажимаю «Синхронизировать», Then запуск идёт в фоне, на странице виден статус «синхронизация…» и она обновляется по завершении.
- Given синхронизация уже идёт, When запускаю повторно, Then получаю отказ (нет параллельных запусков).
- Given репозиторий пуст, ветка не существует или провайдер вернул 401/5xx, Then статус «ошибка»/предупреждение с текстом причины, уже загруженные данные сохраняются.
- Given повторная синхронизация, Then обрабатываются только новые коммиты (инкрементально).
- Given viewer, Then кнопки синхронизации нет, а POST отклоняется с 403.

### US-04. Фильтр по периоду и команде
**Как руководитель, я фильтрую метрики по периоду и команде.**

- Given дашборд, When выбираю пресет (дни) или даты «с/по», Then метрики пересчитываются за этот период.
- Given заданы команды в настройках, When выбираю команду, Then метрики считаются только по её участникам.
- Given «с» позже «по» или неверный формат даты, Then система сообщает об ошибке, а не показывает пустой/неверный отчёт.

### US-05. Отчёты
**Как руководитель, я формирую и скачиваю отчёт за период.**

- Given я admin, When создаю отчёт на странице «Отчёты», Then он сохраняется в списке с периодом и временем создания.
- When открываю отчёт, Then могу получить его в форматах HTML, Markdown, CSV, JSON (`?format=`).
- Given настроен `REPORT_INTERVAL`, Then отчёты создаются автоматически по расписанию.

### US-06. Рекомендации
**Как руководитель, я получаю понятные выводы и рекомендации.**

- Given метрики за период, Then блок «Выводы и рекомендации» содержит пункты с уровнем (критично / предупреждение / информация / хорошо) и советом.
- Given bus factor = 1 при достаточном числе файлов, Then показывается критическая рекомендация с указанием владельца файлов.
- Given тренд ухудшается против прошлого периода, Then это отражается в рекомендациях; рекомендации всегда ссылаются на метрику-основание.

### US-07. Баллы Zerocracy
**Как разработчик, я хочу понимать, за что получаю баллы.**

- Given политика начислений (по умолчанию или JSON из `ZEROCRACY_POLICY`), Then баллы считаются за влитые MR, ревью, закрытые задачи и связь коммитов с задачами; штрафы — за огромные MR, влитие без ревью, просроченные задачи.
- Then для каждого участника показан breakdown по видам начислений и доля в общей сумме.
- Given одни и те же входные данные и политика, Then журнал начислений идентичен при повторном расчёте (воспроизводимость).

### US-08. Подбор исполнителя задач
**Как руководитель, я вижу кандидатов на открытые задачи.**

- Given в «Т1 Код» есть открытые задачи, Then для каждой показаны кандидаты со счётом и причиной (опыт в файлах/метках × текущая загрузка).
- Given включён `AUTO_ASSIGN`, Then лучшая кандидатура назначается в «Т1 Код» автоматически; иначе — только рекомендация.

### US-09. Объединение авторов
**Как руководитель, я объединяю дубли авторов (разные e-mail одного человека).**

- Given в настройках список авторов, When выбираю двух и объединяю, Then их коммиты, MR и ревью учитываются как один автор.
- Then объединение видно во всех метриках, баллах и таблицах; действие доступно только admin.

### US-10. Защита от плохих данных и безопасность
**Как владелец сервиса, я уверен, что некорректные данные и ввод не ломают систему.**

- Given коммиты с датой в будущем/слишком далёком прошлом, Then они отбрасываются с предупреждением.
- Given URL вида `http://127.0.0.1/...`, `ftp://...`, локальный путь, Then проект не создаётся (защита от SSRF).
- Given POST без CSRF-токена или открытый redirect в `next`, Then запрос отклонён.

## 5. Definition of Done

История или задача считается выполненной, если:

- [ ] реализован функционал, критерии приёмки выполнены и проверены на реальных данных;
- [ ] есть автотесты (unit и/или HTTP); `make test` (`go vet` + `go test -race ./...`) проходит;
- [ ] для интеграций и парсера проверен хотя бы один сценарий на реальном репозитории (`make test-integration`);
- [ ] `gofmt -l .` не выдаёт файлов, `make lint` проходит;
- [ ] ввод пользователя валидируется; нет секретов в коде и репозитории;
- [ ] UI проверен: светлая/тёмная тема, узкий экран, пустое состояние, состояние ошибки;
- [ ] метрика/поведение описаны в документации (`docs/`), формула видна в интерфейсе;
- [ ] код прошёл review другим участником команды и слит в основную ветку через MR в «Сфера.Код»;
- [ ] задача в «Сфера.Задачи» переведена в «Готово», результат показан на очередном Показе.
